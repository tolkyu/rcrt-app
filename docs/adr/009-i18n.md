# ADR-009 — Internationalisation (next-intl, `uk` only)

- **Status:** Accepted
- **Date:** 2026-10-30
- **PRD:** §1 (Ukrainian UI), UI-05, OFFER-02, NOTIF, PERF-04, `CLAUDE.md` §2

## Context
- All UI copy, emails, PDFs and notifications in Ukrainian; code/DB/API identifiers in English.
- `uk-UA` number/date/currency formats; time shown in Europe/Kyiv (user timezone column default `Europe/Kyiv`).
- Structure must allow adding `en` later without refactoring. Keep JS small.

## Options
| Option | Pros | Cons |
|---|---|---|
| **A. next-intl, single locale, no locale prefix** | RSC-native, ICU plurals, per-namespace client messages, typed keys | — |
| B. Hard-coded Ukrainian strings | Fast to write | Untestable, blocks `en`, violates DoD |
| C. i18next / react-intl | Mature | Heavier client runtime, weaker RSC story |

## Decision
**A.**

| Topic | Rule |
|---|---|
| Routing | `locales: ['uk']`, `defaultLocale: 'uk'`, `localePrefix: 'never'`; adding `en` later = new locale + messages file, no route changes |
| Messages | `messages/uk.json`, namespaced (`common`, `nav`, `vacancy`, `candidate`, `pipeline`, `enums`, `errors`, `notifications`, `email`, `pdf`, `stats`, `settings`) |
| Type safety | next-intl `AppConfig` augmentation with `typeof uk` → missing/unknown keys fail `pnpm typecheck` |
| Server | `getTranslations(namespace)` in RSC, route handlers, emails, PDFs, notifications (`createTranslator` with the same messages) |
| Client bundle | `NextIntlClientProvider` receives only namespaces used by client components on that route (`pick(messages, [...])`) |
| Enums | DB/API enums in English (`SUBMITTED_TO_TL`); labels via `enums.stage.SUBMITTED_TO_TL` |
| Errors | API returns stable `code`; UI renders `errors.<code>`; server never sends Ukrainian prose in API errors |
| Plurals | ICU `{count, plural, one {# день} few {# дні} many {# днів} other {# дня}}` |
| Formatting | next-intl `useFormatter`/`getFormatter` (built-in `Intl`) with `timeZone` = user's tz (default `Europe/Kyiv`), `uk-UA` currency/number/date/relative time. No extra formatting library on the client |
| Date maths | `date-fns` + `@date-fns/tz` (`TZDate`) for Kyiv calendar-day logic in domain code (probation days, reminders, stats buckets) |
| Lint | `react/jsx-no-literals` (allow-list for punctuation/icons) on `app/` and `components/`; CI script fails on unused/missing keys |
| PDFs | `@react-pdf/renderer` registers a Cyrillic-capable font (same family as UI, TTF self-hosted) — default PDF fonts lack Cyrillic |
| Emails | React Email templates read from `email.*` namespace; subject + body Ukrainian; dates formatted in Europe/Kyiv |
| Content | User rich text is not translated. Stored as **ProseMirror JSON** validated by a strict Zod schema (allowlisted nodes/marks), never HTML; rendered through React only (lint bans `dangerouslySetInnerHTML`); link marks and URL fields accept only `https:` / `mailto:` (DG-13) |
| Escaping | React Email and react-pdf escape interpolated values; message params are plain values, never HTML; search input escapes `% _ \` for `ILIKE`; lint bans `sql.raw` with input (DG-13) |

## Hot path & budget
- Per-route client messages typically < 5 KB gz; formatting via native `Intl` (0 KB).

## Consequences
- (+) Compile-time key safety, no hard-coded strings, ready for `en`.
- (−) Message namespaces must be curated per route to keep client payload small.
