# ADR-019 — Authorized vacancy content read

- **Status:** Security contract approved; implementation based on green CI `44474819422` at `b0e7c3e`, pending final implementation reviews.
- **Date / scope:** 2026-11-18; VAC-01/VAC-08, D75/D92/D98/D133; follow-on to [ADR-018](018-vacancy-content-editing.md).

## Context and decision

`VacancyDetail` omits documents. Its existing `vacancyDetailQuery`, request-cached `loadVacancy` and card/list preview prefetch share `['vacancy',id]`. Extending that DTO would send two potentially 50,000-character JSON documents to every prefetched preview and change existing draft/detail consumers. The content editor/view in [UX design](../ux/wireframes/vacancy-content-edit.md) needs an independent document/version/eligibility baseline.

**Add `GET /api/v1/vacancies/{vacancyId}/content` beside the existing PATCH.** Keep existing detail/list contracts and prefetch unchanged. Reuse ADR-018 schemas, central authorization and `/content` service module; no new permission, migration, renderer or generic read framework.

## Read and eligibility contract

| Response     | 200 `VacancyContentRead`: existing `vacancyContentSchema` extended with `status` from the existing vacancy status enum and boolean `canEditContent`. | Documents    | Both keys always present, each canonical `RichTextDoc` or NULL. NULL is stored absence; an empty paragraph remains a document. No omitted-as-empty fallback, HTML serialization or second sanitizer. Reuse existing rich-text limits/normalization.                                                                      |
| Read policy  | Exactly existing `vacancyReadWhere`: GLOBAL/VERTICAL/OWN/ASSIGNED/UNASSIGNED_OPEN where already granted, including mixed-role union. No edit permission is required to read documents; HR/Head HR and unassigned-OPEN Recruiter readers can read without editing. No contacts/bonus/audit expansion.                     |
| Private rows | An author's DRAFT or never-opened CANCELLED draft is readable only while existing author eligibility permits it. Another author's private row remains 404 even for Admin/Head Recruiter; no new draft access.                                                                                                            |
| Closed rows  | Published FILLED/CANCELLED remain readable to existing visible readers. D133 restricts editing, not reading; status is returned and `canEditContent:false`.                                                                                                                                                              |
| Capability   | True only for OPEN/ON_HOLD and the existing central content-edit permission union on the same resource facts. DRAFT is always false; author-only draft editing remains separate. No role-string, creator or urgency shortcut.                                                                                            |

A visible read-only caller gets 200 with false, not 403. Pure Admin aal1 retains route-level MFA denial; mixed-role aal1 uses only active grants, never withheld GLOBAL grants. |

This adds no access policy. Custom/mixed grants keep existing central scope semantics; custom-role persistence remains outside the slice. The flag is authoritative for this server read, advisory for a later write: PATCH still rechecks fresh actors/relationships/status/version under ADR-018 locks.

## One snapshot and bounded query

`getVacancyContent(ctx,id)` requires read permission and uses `findVisibleVacancyOrThrow` with `vacancyReadWhere` and a new narrow `findVacancyContent(db,scope,id)` in the existing repository. One SQL statement selects live row ID, documents, version, updatedAt, status and only the internal facts needed by `VacancyRef` (vertical, creator, TL, openedAt, recruiterInitiated, assigned IDs). Parse typed row/doc boundaries; do not return internal authorization facts. Applications are absent at this phase; preserve the existing content writer's resource-fact convention.

The assignment IDs come from a correlated PK-indexed subquery in **that same SELECT**. Do not combine a pre-read detail version with later documents, or call `listRecruiterIds` in a second statement. PostgreSQL's statement snapshot makes documents/status/version/relationships coherent. No write transaction, user/vacancy lock or duplicate initial `readVacancy` is needed. The request's already-verified auth context follows existing read semantics; do not claim serializable role revocation during an in-flight read.

Hot path: existing principal/session lookup plus one scoped vacancy PK read and assignment PK lookup; no scans, per-assignee fetches or new indexes. Ordinary existing session activity touching is unchanged; GET creates no vacancy event/audit/change_feed rows and consumes no vacancy write bucket.

## Cache and UI consumption contract

- HTTP success and problems retain `Cache-Control: private, no-store` from `defineRoute`; retain `dynamic='force-dynamic'`. No shared Next Data Cache, CDN/ETag/304 contract, localStorage or persisted Query cache for documents. The existing `apiRequest` uses same-origin credentials and response-schema validation.
- Add `queryKeys.vacancyContent(id) = ['vacancy',id.toLowerCase(),'content']` and `vacancyContentQuery(id)` in its own small module. Existing `refreshVacancy` prefix invalidation already reaches this key; do not put documents into the detail key or list metadata.
- Content query uses `staleTime:0`, `gcTime:0`, refetch on mount/focus/reconnect, `retryServerErrors`, AbortSignal and `background:true` like existing detail queries. No placeholder/previous-vacancy data. This is a document-specific override; shared QueryClient defaults remain unchanged.
- Add a request-cached server `loadVacancyContent` beside existing `loadVacancy`, calling the same service directly with `requireSession`; lower-case IDs and map only NotFound to null. Future card/editor RSC consumes it through the per-request QueryClient/HydrationBoundary with the exact read DTO/key; metadata and content loads can run in parallel. Do not add content prefetch to list previews. No existing page is changed by this preparatory API/query slice.
- Future editor initialization requires a successful current content read; use **its** version/status/flag together, never a version from the detail cache. A stale cached capability cannot enable saving while the entry read is pending/failed. A dirty editor never silently adopts background documents/version; use the UX stale/discard flow.
- PATCH returns fewer fields than GET: do not replace the GET cache with its response or fabricate status/eligibility. The later mutation hook can adopt canonical PATCH documents/version as its local clean baseline, then invalidate/refetch content and inherited detail/list keys; eligibility is refreshed from GET before another authorized edit.
- On confirmed read-access/session denial, future consumers hide documents immediately, cancel pending content work and remove this content query plus local editor baseline/drafts; do not continue rendering retained `query.data` behind a 401/404. On PATCH 403 refresh GET: retained read access may yield documents with false, or an independent mixed-role grant may still yield true. UI consumption must handle both. Different-user session transitions must never reuse another user's mounted content state.
- Revocation is observed on the next authenticated read/refocus/reconnect or explicit denial; no Realtime bridge currently exists. `no-store` prevents HTTP reuse, not retention of bytes already delivered. This slice promises neither instantaneous remote erasure nor new polling. PATCH remains the write authority after any cached read.

Integration uses the exclusive shared lock. No full suites/build/runtime tests during this design task; future UI gets shared-screen E2E, bundle and D125 screenshot gates.
