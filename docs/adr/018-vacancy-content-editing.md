# ADR-018 — Published vacancy content editing

- **Status:** Architecture contract ready for security review and implementation
- **Date:** 2026-11-18
- **PRD:** VAC-08, D75/D78/D92/D93/D133; STORY-VAC-01-2a
- **Baseline:** `bc8f061`; preserves ADR-012 converse locking and ADR-017 assignment writers.

## Context and options

The existing `PATCH /vacancies/{vacancyId}` is explicitly `updateVacancyDraft`: author-only gates, a broad draft schema and `VACANCY_NOT_DRAFT` for published rows. `vacancy.update` has GLOBAL/VERTICAL/OWN scopes; Recruiter has no update grant. Rich-text persistence, document validation, versioned updates and `vacancy.updated` already exist.

| Option                                            | Trade-off                                                                                                                          |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Broaden the existing PATCH                        | Requires changing private-draft route gates and dispatching two field contracts; risks draft disclosure and published overposting. |
| **Separate content PATCH, reuse existing layers** | Preserves the draft contract; one narrow service and schema, sharing locks, validation, events and update helper.                  |

## Decision

### Endpoint and payload

`PATCH /api/v1/vacancies/{vacancyId}/content`, operation `updateVacancyContent`, through `defineRoute`. Gate with `vacancy.read`; do not change the route factory to introduce an OR gate. The service performs scoped resource authorization. Keep the existing draft PATCH unchanged.

Reuse `richTextDocSchema` unchanged for both request and response. It allows ProseMirror doc JSON with paragraphs, headings 1–3, bullet/ordered lists; text/hardBreak, bold/italic/link marks; at most 50,000 serialized JSON characters **per document**. Inherited nested attribute stripping remains unchanged. No sanitizer, parallel validator, new limits or renderer is needed. Use parsed documents for comparison and storage.

### Central permission contract

Add `vacancy.content.update` to `server/authz/permissions.ts` as a normal vacancy write with legal scopes GLOBAL/VERTICAL/OWN/ASSIGNED, without an additional MFA flag. Global grants still require aal2 through existing `buildAuthContext` rules.

- Built-ins: Recruiter receives only ASSIGNED for this new permission. Admin receives GLOBAL through its existing automatic catalog grant. Head Recruiter and Team Lead keep their existing VERTICAL/OWN `vacancy.update`; no duplicate grants are required. HR, Head HR and Finance receive none.
- Central helper in `server/authz/vacancy-content.ts`: `canEditVacancyContent(auth, resource: VacancyRef): boolean` = `can(auth, 'vacancy.update', resource) || can(auth, 'vacancy.content.update', resource)`. It decides permission, not status; service checks status afterwards. Use existing typed facts and schema-derived types, without inventing an application state or raw role-name checks.
- The existing `can()` scope evaluation supplies vertical/OWN/ASSIGNED checks and unions mixed-role grants. A read grant, creator identity or `vacancy.self_assign` never permits content editing. Mixed-role actors retain any independently applicable grant; unassignment cannot cancel an independent own-TL/Head grant.
- Custom definitions, when supplied through the existing authorization mechanism, follow the same legal scopes and union; no built-in role-name bypass. This slice does not introduce custom-role persistence/hydration. Do not broaden `vacancy.update` scopes or give it to Recruiter; urgency/status/team/bonus/probation permissions remain unchanged.
- Add the permission to the documented and tested catalog matrix. New row: Admin G, Head Recruiter denied, Recruiter ASSIGNED, Head HR/HR/Team Lead denied, Finance 404. These are grants of the **new action**, not the effective content endpoint union. Add an ASSIGNED-only fixture token; retain the generic `vacancy.update` row unchanged.

### Transaction and error order

1. Require `vacancy.read`; consume the shared write limit; parse the shared content schema and ID (service remains safe when called directly).
2. Begin transaction. `readVacancy(ctx, tx, id)` establishes visibility: unknown/deleted/foreign/private draft → 404. Use its vertical only as preliminary context; it does not authorize the eventual write.
3. `lockAuthors(ctx, tx, [])` locks the actor FOR SHARE, rechecks active state and reloads role grants. Then `lockVacancy(tx, id, {docs:true})` acquires NO KEY UPDATE; absent/deleted → 404. Never acquire a user lock after this vacancy lock.
4. Read `listRecruiterIds(tx, id)` **after** the vacancy lock. Build authoritative resource facts from this row/set. Check the permission union with fresh auth; deny 403 when visible but action is not granted. Initial invisible scope is 404; a grant/assignment lost after the initial visible read may return 403. Never decide from the pre-lock recruiter list or request context alone.
5. Check status (409 `VACANCY_CONTENT_LOCKED`), then `expectedVersion` (409 `STALE_STATE`), then compare supplied canonical documents with `isDeepStrictEqual`. A stale same-value request is still 409. A current-version no-op returns 200 with no vacancy update, version/timestamp change, success audit or event.
6. For a real change call existing `updateVacancy(tx, id, {status:row.status, version:body.expectedVersion}, changedDocumentsOnly, now)`. A missed compare-and-set → 409 `STALE_STATE`. Increment once. No author predicate: published content rights derive from current grants and relationships.
7. Append the event and audit below in this transaction. Before returning, `readVacancy({...ctx, auth:freshAuth}, tx, id)` confirms current read scope, as ADR-012 requires; a 404 aborts the whole transaction. Return the locked/merged canonical documents plus committed version and injected UTC update time. The no-op follows the same fresh scoped-read check.

Assignment writers already serialize on the parent vacancy lock. If removal commits first, the content editor sees the new set and cannot retain ASSIGNED permission; if content obtains the lock first, its write commits before removal. User locks prevent concurrent deactivation/role removal from invalidating fresh authorization mid-write. Two distinct content changes with one version produce one winner and one stale loser; the loser writes no history. Status/urgency/team version bumps also invalidate content writes. No new repository, migration, lock helper or transaction framework.

### Acceptance and review gates

- Schema: either/both fields, missing preserved, NULL clears, empty paragraph retained, replacement not merge; empty/version-only payload and every overposted field denied; malformed/oversized docs, controls and unsafe links rejected with no submitted text in problems/logs. Reuse existing rich-text tests rather than duplicate the entire validator suite.
- Authz: allowed assigned Recruiter/own TL/scoped Head/Admin aal2; denied visible unassigned Recruiter/HR/Head HR; foreign vertical/other TL/unknown/deleted/private draft 404; pure Admin aal1 inherited MFA response; mixed-role/vertical union and withheld GLOBAL grants; new permission cannot authorize urgency/status/team/probation. Cover synthetic custom scopes centrally without claiming custom persistence exists.
- Integration: both live statuses; all closed/draft outcomes; no-op/stale no-op; version increments once; exact changed fields and untouched columns; one event/audit and no raw content in history; safe canonical response; session/deactivation, CSRF, UUID/body and shared rate-limit behavior through the route factory.
- Deterministic races: two content writers; content versus unassignment with another recruiter retained (prevents reverting to unassigned-pool visibility), status close and role revocation. Assert actual serialized outcome/unchanged loser state and no loser history; avoid timing-only sleeps. Add rollback evidence for failed history insert or fresh-scope failure.
- Run typecheck, lint and touched unit/integration tests only; integration under the shared exclusive lock. Include existing draft route/lifecycle and urgency/assignment/status permission regressions affected by catalog changes. Separate High code review, security review and focused QA are required for isolation/PII. No full suites/build/screenshots in design or slice; CI and V-block gates follow D129.

## Consequences and implementation instruction

Closed-state policy is resolved by D133; no owner policy question remains. Full content snapshots are deliberately absent from audit/events; a future history UI must not promise reconstruction from these events. Main risks are accidentally broadening Recruiter operational permissions, trusting assignments before the lock, or persisting free text into history.

Delegate the exact implementation files above to one High critical specialist using the senior-fullstack role, with tests and generated contracts. Preserve concurrent documentation edits and existing draft behavior. Obtain security review of this contract before finalizing implementation; reviewer findings may narrow file edits, but any product-policy change returns to the owner. No UI, custom-role module, general vacancy edit, migration or candidate work belongs to this slice.
