### STORY-VAC-01-2a: Update published vacancy content

As an assigned Recruiter in a vertical, I want to correct a vacancy's description and requirements so that colleagues see current recruiting information.

**Proposed implementation boundary:** API/service/repository behavior for `OPEN` and `ON_HOLD` only (owner answer Q-195/D133). No new screen. Preserve author-only `DRAFT` behavior (D92), cancelled-draft immutability (STORY-VAC-01-3), existing dedicated status/urgency/team writes, and field-specific permissions. Mixed-role users obtain the union of applicable grants using central authorization; a read grant alone never grants editing.

| Case                    | Given / When / Then acceptance criteria                                                                                                                                                                                                                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Allowed actors          | Given an active assigned Recruiter, own Team Lead, Head Recruiter in the vacancy vertical, or Admin satisfying existing MFA rules, when they submit a permitted content patch and current version for an accessible `OPEN`/`ON_HOLD` vacancy, then only supplied content fields change and omitted values remain intact. |
| Scope denial            | Given an unassigned Recruiter, foreign-vertical user, Team Lead of another vacancy, Finance, or HR/Head HR with read rights only, when they patch content, then no write/audit/event occurs; out-of-scope resources return the inherited 404, while in-scope action denial follows the existing API convention.          |
| Restricted fields       | Given any content editor, when the payload also contains status, urgency, vertical, recruiters, Team Lead, bonus/reward, probation or another field outside this endpoint contract, then validation rejects the whole patch atomically. Broader role permissions do not widen this two-field contract.                   |
| Validation              | Given malformed identifiers/version, unknown keys, wrong field types or invalid rich-text content, when submitted, then shared approved content validation rejects the request; no partial save or PII-bearing log is produced. Reuse existing create/draft rich-text limits and sanitization; do not invent new limits. |
| Race                    | Given two writers with the same current version, when both change content, then one change commits and the other receives `409 STALE_STATE`; only the winner creates history. Authorization and assignment are rechecked in the write transaction so a concurrent unassignment cannot retain editing rights.             |
| No-op                   | Given a current version and unchanged submitted content, when saved, then success creates no version increment, audit row or event, following the vacancy write convention.                                                                                                                                              |
| Missing/deleted/session | Given an unknown or soft-deleted vacancy, then return the inherited 404; given a deactivated user or invalid session, then existing session guards deny access; no mutation occurs.                                                                                                                                      |
| Draft isolation         | Given another author's `DRAFT`, even Admin cannot edit it; given the author's draft, the existing draft-edit behavior remains intact and this slice does not broaden access.                                                                                                                                             |

**Closed-state negative AC (D133):** Given an otherwise authorized editor and a published `FILLED` or `CANCELLED` vacancy, when description/requirements are patched, then refuse the write without version/audit/event changes. `FILLED` must use the existing authorized reopen flow first; `CANCELLED` stays immutable and cannot reopen (D130). Keep existing draft PATCH behavior, including immutable cancelled drafts. The ADR defines the specific refusal response; this owner decision does not set editing policy for other fields.

**API contract — [ADR-018](../adr/018-vacancy-content-editing.md):** `PATCH /api/v1/vacancies/{vacancyId}/content` preserves the existing author-only draft PATCH. Strict body: `expectedVersion` and at least one of `descriptionDoc`/`requirementsDoc`; omission keeps, `null` clears, supplied canonical rich-text JSON replaces the document. Reuse `richTextDocSchema` and its 50,000 JSON-character limit per document. Closed/private-draft outcomes follow the ADR; authorized closed requests get `409 VACANCY_CONTENT_LOCKED`.

**Data and events:** a real change increments version once and reuses one `vacancy.updated` event with only changed field codes. One same-transaction audit row records before/after versions and changed field codes, never rich text, URLs or content snapshots. The response is `{id, version, updatedAt, descriptionDoc, requirementsDoc}`. Fresh central permission union (`vacancy.update` or new narrow `vacancy.content.update`) and assignments are checked under actor-then-vacancy locks. No notification delivery (D93), status-counter/statistics effect, candidate/application change or probation recalculation. Reuse existing UTC timestamp handling; no date arithmetic is introduced.
