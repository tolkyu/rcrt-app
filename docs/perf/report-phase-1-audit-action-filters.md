The first implementation exceeded the audit limit by 719 bytes. Moving the date form/reason helper alone reduced audit to **180.62 kB**, still 617 bytes over budget. The production manifest confirms the date form is already in an async chunk, so disabling SSR would not remove it from this initial graph. A shared actor/action trigger removes duplicate hooks, label/clear/chevron markup while preserving lazy picker boundaries and independent 44 px mobile targets; measured audit was **180.59 kB**, still 593 bytes over budget. Native associated labels with identical typography replaced the two eager Radix Label imports, bringing audit to **180.12 kB**, still 120 bytes over budget. Field-label extraction/parser deduplication measured **180.08 kB**, still 81 bytes over. Removing the unused `@date-fns/tz` side-effect module from the client graph (server-only bounds split, no behavior change) saved **1,610 bytes**: audit **178.47 kB**, 1.53 kB headroom. Audit-specific chunks now: page 8.46 kB + split chunk 2.01 kB gz (was 3.61 kB). Browser regression checks are coordinated by QA.

## Read-only local query plans

Executed actual `listAuditEntries(...).toSQL()` statements with `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` in a read-only transaction. `parseLocalDatabaseTargets` validated `APP_ENV=local`, loopback runtime/migration endpoints and the `app_rw` runtime account before connecting. No fixtures, mutations, resets or secrets were printed.

Local PostgreSQL sample: **433 audit rows**, **216 security rows**, 13 users, two verticals. Cases intentionally omit time/actor restrictions to exercise the combined predicates. All four return through the same joined list statement, `LIMIT 51`. Timings below are single local database executions; **they are not endpoint P95**.

| Case                                                        | Actual audit access / top-level order                                                                           | Matching/output rows | Planning / execution | Root buffers hit/read |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------: | -------------------: | --------------------: |
| `user.invited`, `auth.login_succeeded`, `user.mfa_enrolled` | `audit_log_occurred_idx` Index Scan; nested-loop label joins; Limit. Action predicate removes 94 scanned rows.  |      51 / 51 at stop |     1.063 / 0.710 ms |               131 / 0 |
| Security only                                               | `audit_log_occurred_idx` Index Scan; nested-loop label joins; Limit. Prefix predicate removes 103 scanned rows. |      51 / 51 at stop |     0.465 / 0.314 ms |               134 / 0 |
| Same three actions AND security                             | Audit Seq Scan → hash label joins → Sort → Limit; 267 rows removed by filter.                                   |             166 / 51 |     0.291 / 1.641 ms |                40 / 0 |
| `user.invited`, `vertical.created` AND security             | Bitmap Index Scan on `audit_log_action_idx` → Bitmap Heap Scan (15 rows rejected by security) → Sort → Limit.   |                0 / 0 |     0.337 / 0.072 ms |                 5 / 0 |

`audit_log_action_idx(action, occurred_at DESC, id DESC)` and the ordered occurrence index already exist. The planner used different paths by selectivity; it did **not** use the action index for every multi-action case. Prefix checks can be residual filters, so a bounded response does not bound rows examined. This tiny, warm local sample does not establish large-data performance or justify a new index. T8 must measure selective, sparse-security and deep-cursor workloads at realistic scale before deciding whether a security-specific index is needed. Ignored local capture: `.cache/perf-audit-actions.ts` / `.cache/perf-audit-actions-results.json`.
