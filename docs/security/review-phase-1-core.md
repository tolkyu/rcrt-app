# Security review — Phase 1 server core (T3) and DB fixes

- Date: 2026-10-31 · Reviewer: security-engineer
- Scope: commits `36949d9` (migration 0003, exact grant-matrix test, seed guard, tooling errors) and `e6be251` (`server/authz`, `server/context`, `server/http`, `server/audit`, `server/events`, `middleware.ts`, `app/api/v1/{me,verticals}`, OpenAPI/Postman artifacts). Uncommitted T4 files are reviewed separately in `docs/security/t4-auth-requirements.md` §0. Where the working tree already fixes a T3 finding, that's noted.
- Inputs: threat model (T-*, DG-01..22), `docs/authz-matrix.md`, ADR-002/003/005/006, PRD §2.3, §13 SEC, §14 (D13, D22, D30, D35, D40, D41, D53, D63).
- Method: source review against the matrix and owner decisions; static read of the SQL predicates, grants and migration; no hosted access; no code changed.

## Verdict

The authz core is sound in structure: one module, fail-closed context, grants keyed per permission and scope, route-level 404, aal2 gating as D63 requires, exact DB grant test. The problems are **rule-data defects** (one High, two Medium) and **API-design hazards** that later phases will hit. **T3 can't be marked done until SEC-CORE-01…03 are fixed.** SEC-CORE-04…09 are gates that must be closed before the first Phase 2 endpoint that uses them.

## Gates before the first Phase 2 endpoint (Medium)

| ID          | Finding and evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SEC-CORE-04 | **Self-benefit guard is opt-in.** `assertCan` (`can.ts:174`) accepts the 7 `selfBenefit` permissions without beneficiaries. A service that forgets `assertNotSelfBenefit` (`can.ts:213`) compiles and passes the matrix tests. The guard also only checks the actor against the ids passed in, so a split edit that removes a co-recipient isn't covered unless the caller passes the old set.                                                                                                                                                     | Exclude `selfBenefit` codes from `can`/`assertCan` at type level, and add `assertCanActOn(ctx, permission, resource, beneficiaries)` as their only API. For split/reassign, beneficiaries = old ∪ new recipients/owner. Keep the DB CHECKs (`approved_by <> recipient_id`, `paid_by <> recipient_id`) in Phase 4.                                                                                                                                                                                                                           |
| SEC-CORE-05 | **Detail fetch can be scoped by a write permission.** `findVisibleOrThrow(load, scope)` (`server/authz/scopes.ts:82`) takes any SQL. HR/HHR write grants are `VERTICAL` (`permissions.ts:78, 88`; `roles.ts:137-150, 174-180`) while their read grants are `V≥P`. A detail query scoped by `scopeWhere(ctx,'polygraph.schedule',…)` loads applications HR can't open, and answers 409/403 instead of 404 (existence oracle, VIS-02).                                                                                                               | Change the API to `findVisibleOrThrow(ctx, readPermission, adapter, load)`, where `readPermission` is restricted to `write:false` codes and the scope is computed inside. Optionally narrow the HR/HHR write scopes to `V≥P`. Add a contract test: every detail route fetches with a `.read` permission.                                                                                                                                                                                                                                    |
| SEC-CORE-06 | **Generic `23505 → 409 ALREADY_EXISTS`** (`server/http/map-error.ts:22`). Once the DG-19 unique dedupe indexes and user-email uniqueness exist, any create/update that hits them tells the caller "this person/email exists somewhere", across verticals. That bypasses the DG-11 HIDDEN-match limits and the security event (T-Z07).                                                                                                                                                                                                              | Map 23505 only for an allowlist of constraint names whose existence is already visible to the caller. Otherwise return 500 and log the constraint. The candidate dedupe path must go through the dedupe service (rate limit + audit).                                                                                                                                                                                                                                                                                                       |
| SEC-CORE-07 | **PII split is a denylist, and audit `details` isn't purgeable.** The event payload guard (`server/events/index.ts:96-161`) matches exact keys only (`candidateEmail`, `phoneNumber`, `meetLink`, `message`, `description`, `additionalTerms` all pass). `entity_event` is append-only, so a mistake can never be purged (T-D11, ARCH-04). Audit `details` (`server/audit/index.ts:18`) has no guard, and `app_purge` can only null `before`/`after`. `candidateId` is optional (`audit/index.ts:15`), so candidate-related rows can escape purge. | Per-event-type `.strict()` payload schemas (discriminated union on `type`, allowlisted fields, P3-09) before the first Phase 2 event writer. Until then, a case-insensitive substring guard (`email\|phone\|telegram\|name\|comment\|note\|text\|url\|link\|address\|file\|feedback\|reason\|message\|description\|terms\|salary` outside `sensitivity=SALARY`). Apply the same guard to audit `details`. Require `candidateId` when `entityType ∈ {candidate, application, interview, polygraph, offer, probation, comment, file_object}`. |
| SEC-CORE-08 | **Raw role assignments on `AuthContext`** (`server/authz/context.ts:23`) include ADMIN/FINANCE even at aal1, with no vertical binding. A future `ctx.auth.roles.some(r => r.role==='ADMIN')` would bypass both aal2 (ADR-002 §10) and DG-10. `ResolvedGrant.roles` (`context.ts:18`) isn't used by any decision.                                                                                                                                                                                                                                   | Remove `roles` from `AuthContext` (keep it only for `/me` via a separate DTO helper) and remove `ResolvedGrant.roles`. Add a lint rule banning role-string comparisons outside `server/authz/**`.                                                                                                                                                                                                                                                                                                                                           |
| SEC-CORE-09 | **Custom roles skip MFA and can be global.** MFA gating keys on built-in role codes (`context.ts:64-66`). `user_role_scope_chk` (`server/db/schema.ts:124`) allows `custom:*` with `vertical_id IS NULL`, and `buildAuthContext` then accepts GLOBAL grants (`settings.users.manage`, `audit.read`, `bonus.mark_paid`). In Phase 2 an Admin-defined global custom role would act at aal1.                                                                                                                                                          | Gate by permission, not role: any GLOBAL grant, plus all `settings.*`, `audit.read`, `bonus.*` writes and `candidate.purge`, need aal2. Forbid global custom roles until the owner decides. Unit test.                                                                                                                                                                                                                                                                                                                                      |
