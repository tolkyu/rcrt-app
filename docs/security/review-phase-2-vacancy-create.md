# Security review — Phase 2 V2b S1 (vacancy creation, author-only drafts, idempotency, rich text)

Date: 2026-11-09. Scope: ADR-012 addendum, VAC-01, D87/D89/D92/D98, DG-13, SEC-CORE-07, migration 0014. Reviewed the uncommitted working tree on `phase-2` (PNGs ignored): `POST /api/v1/vacancies`, `vacancyReadWhere`/`can()` draft rule, `idempotency_key` table and `Idempotency-Key` handling in `defineRoute`, `lib/schemas/rich-text.ts`, lock helpers, migration grants. No application source was changed. I ran the two new unit suites (`vacancy-author`, `vacancy-create-schema`: 87 passed) and a throwaway Zod probe (scratchpad) against the real schemas. Integration tests need a database and were not run.

**Verdict: approved, no Critical or High findings, no blocking item.** Draft isolation, scoping, mass-assignment and idempotency isolation hold on every path I traced. Two Medium items (volume cap, draft audit trade-off) and three Low items should be scheduled; SEC-VC-02 is a cheap fix worth taking in the same commit.

| SEC-VC-01 | Medium             | No volume cap on created rows. | SEC-VC-02 | Low                | Link `href` is validated only by `^(?:https:\/\/\|mailto:)[^\s<>"']+$`. ### SEC-VC-04 trade-off assessment

| Aspect                      | Position                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Why it is acceptable        | D92 states a draft is private to its author, including from Admin. Any audit row visible to the viewer discloses existence, vertical and title. The rest of the visibility surface (list, detail, search, cursor, can()) is consistently closed.                                                                                                                                                                                                                                                           |
| What is not lost            | `entity_event` still gets `vacancy.created` (actor, request id, number, status; no title) in the same transaction, so a database-level forensic trail exists. Titles stay out of events (SEC-CORE-07).                                                                                                                                                                                                                                                                                                     |
| What is lost                | Admin-visible accountability for draft creation, edits and cancellation, and any application path to review or erase orphaned drafts (author deactivated for good).                                                                                                                                                                                                                                                                                                                                        |
| Mitigations (no D92 change) | (1) S2 publish writes the audit row with `createdBy`, original `createdAt` and title, so the trail catches up when the content becomes shared. (2) Draft cancel/delete write `entity_event` rows. (3) Retention: the future purge/retention job and user anonymisation run as system and reach drafts regardless of the draft rule (needs `app_purge` grants on `vacancy`). (4) Optional: an audit row with a visibility marker that the viewer excludes (database-only forensics), if the owner wants it. |
| Residual risk               | Insider can park arbitrary text in a draft with no Admin-visible record; limited by SEC-VC-01 caps. Low impact.                                                                                                                                                                                                                                                                                                                                                                                            |

## Claims verified (no finding)

| Area                                  | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Draft isolation on read paths         | Yes. List, `q` search (title and `V-NNN`), status/priority/vertical filters, cursor/anchor and detail all go through `vacancyReadWhere` (only callers: `listVacancyPage`, `readVacancy`). A foreign draft, a draft of an author who lost the role, and an Admin at aal1 all yield no row, hence 404 on detail and absence in lists. Replay also uses `readVacancy`. No count, statistics or position-count query touches drafts: `listPositions` counts `status = 'OPEN'` only, the open-work guard excludes DRAFT.                                                                                                                                  |
| `can()` rule                          | `evaluate` denies every permission on another user's DRAFT before grant matching, GLOBAL included (`can.ts:155-161`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Vertical IDOR                         | Foreign or unreadable `verticalId` → 404 (`vertical.read`); readable vertical without creating grant → 403 (HR, Head HR, Team Lead; Finance has no `vacancy.read` → 404 at the route). Creator and author kind are derived per vertical from grants, so a Head Recruiter of A who is a Recruiter in B gets the right behaviour in each.                                                                                                                                                                                                                                                                                                              |
| Position and Team Lead from elsewhere | `positionId` unknown, other vertical or outside `position.read` → uniform 400 `invalid_position`; inactive in own vertical → 409 `POSITION_INACTIVE`. `teamLeadId` unknown, other vertical, inactive or not a Team Lead → uniform 400 `invalid_team_lead` (no user enumeration).                                                                                                                                                                                                                                                                                                                                                                     |
| Privilege escalation via body         | `.strict()` on both union branches (unknown keys, including `status`, `source`, `createdBy`, `recruiterInitiated`, bonus fields, `__proto__`, → 400; probe). `teamLeadId` needs `vacancy.team_lead.set`, `probationDays` needs `vacancy.probation_length.set` (403, checked before any write). Status comes only from `mode`; `createdBy`, `source`, `recruiterInitiated` and the auto-assignment are server-derived. Money is digit strings ≤ 15 digits with currency coupling and a DB check.                                                                                                                                                      |
| Probation rule (PROB-05)              | `probationDays` is a per-vacancy default (30..90) for future hires; the endpoint touches no existing end date. Forward rule: a vacancy update must never change an existing probation's end date.                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| MFA                                   | Admin grants are GLOBAL, so `needsAal2` withholds them at aal1 (`context.ts:47`); the route returns 401 `MFA_REQUIRED`; `vacancyAuthorVerticals` reads `ctx.grants`, so an aal1 Admin can neither create nor see own drafts.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Idempotency                           | Unique `(user_id, operation, key)`, so keys are not shared across users or operations and a replay can only return the caller's own vacancy (still re-checked by `vacancyReadWhere`, so a lost role gives 404). Different body → 409 `IDEMPOTENCY_KEY_REUSED` with no data in the body. The claim is in the create transaction; a refused write leaves no key; concurrent duplicates block on the unique index. Key format is enforced in the route (400), the service and a DB check; keys are not high-value secrets and are not logged. Enumeration is impossible across users. Hash covers the normalised, validated body (canonical key order). |
| Rate limiting                         | 30/min per user, consumed before validation and outside the transaction (failed and replayed requests count); runs only after the route's permission gates, so unauthenticated or unauthorised callers never reach the counter. CSRF (`X-CSRF-Protection`, Origin) is inherited from `defineRoute`; body cap 1 MiB with streamed counting.                                                                                                                                                                                                                                                                                                           |
| Rich text bombs and XSS               | Closed allowlist (doc, paragraph, heading 1-3, bullet/ordered list, listItem, text, hardBreak; marks bold, italic, link), fixed nesting depth (≤ 6, no recursion), array caps, text ≤ 5,000, total ≤ 50,000 JSON chars. Probe: 80,000 invalid blocks, 150,000 invalid inline nodes and 60,000 invalid list items each produce one issue in ≤ 3 ms (Zod aborts on the array cap before element errors), so no CPU or response amplification. Nothing renders the docs today. See SEC-VC-02 for `href`.                                                                                                                                                |
| SQL injection                         | None. Search is unchanged and bound; the new `lockUsersShared` interpolates only the bound vertical id; no string concatenation of user input in any new statement.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| PII in logs and events                | `vacancy.created` payload is number, status, source, flag (strict schema); audit `after` carries title, ids and counts but no salary or contacts (OPEN only); logger redacts `body`/`query` and reports DB errors by SQLSTATE only; `ValidationError` returns path and code, never values.                                                                                                                                                                                                                                                                                                                                                           |
| Migration 0014 and grants             | `app_rw` gets `INSERT` on `vacancy` and `vacancy_recruiter` (no UPDATE/DELETE until S2) and `SELECT, INSERT, DELETE` on `idempotency_key`; client roles revoked behind `pg_roles` checks (SEC-VAC-03 pattern fixed); RLS enabled; identity column needs no sequence grant. The `cancelled_at` backfill precedes the new CHECK; manual rollback is documented. DB cannot enforce the draft rule (app role bypasses RLS by design), so the app predicate is the single control (SEC-VC-06).                                                                                                                                                            |
