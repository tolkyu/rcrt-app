## Write contract і точне розділення

1. Основний `entity_event`: існуючий versioned `{v:1, fields:[...]}`, subject/vacancy/vertical IDs, actor/time/requestId. **Жодних** simple values, snapshots, назв catalog/users чи money values. `GENERAL` для D137 vacancy.updated. `fields` — deduplicated у `VACANCY_EDIT_FIELDS` order. Один `salary` при зміні будь-якої частини range; rich codes лише для existing content event.
2. Для нового operational `vacancy.updated` пропонується side schema `data={schemaVersion:1, changes:[{field,old,new},...]}`. Discriminated union по field: `title`, `positionId`, `headcount`, `seniority`, `workFormat`, `employmentType`, `location`, `salary`, `probationDays`. Кожен object `.strict()`, максимум 9 унікальних logical fields; old/new типізовані окремо. `salary` old/new = strict `{minMinor,maxMinor,currency}` (мінорні значення decimal strings/null). Решта — scalar з таблиці. Null — значення «не задано», відсутній key — помилка. Validation історичного old не повинна блокувати коректне виправлення legacy enum: за потреби окремий bounded legacy decoder, **не** arbitrary JSON; перевірити baseline дані міграцією/QA перед rollout, без їх друку.
3. Audit `before/after={version, ...changedLogicalValues}`: той самий typed projection, включно повним `salary` object; details лише `{fields:[canonical codes]}`. Audit не читає side row. Не дублювати unchanged title/location/інших полів; повний salary tuple — один logical field. Обидві копії diff породжуються з одного diff builder locked old та canonical merged new. `candidateId` не підставляти фіктивно: entity vacancy/id достатні для майбутнього vacancy selector.
4. Side `changes.field` мають точно відповідати simple fields основного payload; old≠new. Content-only event не має side row. Read decoder перевіряє type, subject, IDs, schema version і відповідність fields; malformed/unknown version → generic field-name summary без values, safe diagnostic без payload. Missing side row → «Значення недоступні», не припускати автоматично purge (legacy row теж не має side row).
5. `appendEvent` і `writeAudit` викликаються в тій самій транзакції, що update. Новий event-specific side schema потрібен на boundary, а не лише TS тип. `detailsSchema` не розширювати довільними strings. Canonical `salary` є **значенням коду поля**, не зарплатним числом: `server/audit/index.ts:41–58` його вже допускає в `fields`; guard блокує PII-like **ключі**. Strict event payload уже допускає code `salary`, але не salary values. Стара фраза «refuses salary event data» не є описом усього поточного runtime.

**Перевірки та concurrency.** Формат/unknown keys перевіряє strict route schema. Далі shared story order: current visibility 404 → users `FOR SHARE` у sorted order / fresh grants → locked vacancy ownership 403 → OPEN/ON_HOLD 409 → expectedVersion 409 → merged business validation 400 → canonical no-op. Для position change узгодити спільний lock order users→position→vacancy; не захоплювати position після vacancy (create order: `server/services/vacancy.ts:303–307`). Перевірити active/same vertical під lock; у Phase 3 серіалізувати з application attach для D134. Fresh helper уже є (`server/services/vacancy.ts:262–296`), content pattern — `server/services/vacancy-content.ts:64–140`.

Не довіряти client old/new, списку `fields` або edit flags. No-op після нормалізації: 200 без version bump/event/side row/audit; stale equal-value request все одно 409 за story order, version-only patch 400. Невдалий side/audit insert відкатує весь update. Edit-vs-claim/status/probation/інший edit має лише одного переможця на version. При CLOSED перевірка status перед version. Немає audit простих значень для відмови; safe denial metadata може лишатися за existing global policy.

**Server-owned vacancy boundary (read і purge).** Для конкретного server-validated `V` потрібні одночасно `subject_type='vacancy' AND subject_id=V::text AND vacancy_id=V AND candidate_id IS NULL AND application_id IS NULL AND sensitivity='GENERAL'` і **точний** type allowlist: `vacancy.created`, `vacancy.updated`, `vacancy.status_changed`, `vacancy.urgency_changed`, `vacancy.team_lead_assigned`, `vacancy.recruiter_assigned`, `vacancy.recruiter_unassigned`, `vacancy.deleted` (`server/events/index.ts:89–120`). Published envelope vertical має дорівнювати current vacancy vertical; NULL дозволений тільки для author-only draft-era за наявним правилом. Нові D137 writers перевіряють цей boundary перед insert. Unknown types, `vacancy.*` prefix match, `SALARY/POLYGRAPH/BONUS`, інший subject або inconsistent IDs **не** підпадають під D80/GENERAL. Окремий typed decoder на кожен дозволений type; D137 old→new decoder працює лише для `vacancy.updated`, cancel reason — лише `vacancy.status_changed` з `to=CANCELLED`. Ніколи не повертати довільний side JSON для решти types.

Новий timeline: fresh request auth/activity → `findVisibleVacancyOrThrow(vacancyReadWhere)` → **цей boundary** AND `vacancyEventReadWhere` → LEFT JOIN side row → typed DTO. Сам `vacancy_id=V` недостатній; arm `vacancy_id IS NULL` теж не дає дозволу на unbound eventId. Candidate/application/interview/offer події з таким самим vacancy correlation виключені повністю, включно summaries/counts/labels; їхні майбутні readers потребують власного subject scope та sensitivity permissions, не D137 decoder. Це не забороняє майбутню повну timeline за ADR-003, але вона має окремо реалізувати authorization кожного ресурсу. Fresh grants брати на кожен запит, з recheck при очікуванні lock; in-flight fetch має coherent snapshot scoping, не два незалежні незахищені запити. Cursor/limit/count/filter/search також scoped і bounded, без пошуку в приватних values. Server response/cache — private/no-store; purge/access/session loss прибирає timeline query cache та відкриті details; не зберігати diffs у localStorage.

Published history доступна **за поточним правом на картку**, а не historical membership. Draft-era events мають `vertical_id=NULL` і залишаються actor-author-only **назавжди**, навіть після publish; D137 їх не backfill-ить і draft write не отримує audit (ADR-012 `:109`, `server/authz/vacancy-scope.ts:79–96,129–143`). Closed published read дозволено, якщо current scope його допускає; edit lock не є read lock. Recruiter UNASSIGNED_OPEN втрачає доступ після claim/закриття; assigned/TL/vertical readers — за своїм current grant. Future D53 application scope не вмикати завчасно.

Audit detail існує: current Admin aal2, before/after + JSON (`server/services/audit.ts:103–130`, `server/repositories/audit.ts:149–168`). D137 додає event/action-aware strict projection для before/after; raw JSON/copy показує **лише той самий sanitized DTO**. Після purge null лишається null. List не додає snapshots.

## Labels та відсутність витоку

- Field labels і enum labels — allowlisted Ukrainian i18n; «Зарплатна вилка», «Терміновість вакансії», «Випробувальний термін, днів». Money formatter використовує кожну історичну валюту, null явно «Не задано»; не показувати суму з поточною валютою.
- `positionId` label — current catalog name, same vertical lookup після vacancy authorization; inactive catalog теж відображається. Не snapshot назви. Якщо reference недоступний — generic «Посада недоступна», без cross-vertical fetch чи чужих імен. Це історія reference, не гарантія історичного spelling назви catalog.
- `teamLeadId`, recruiter IDs і actor IDs — current user labels після допуску до події, inactive marker D79; без email, contact endpoints або довільних UUID lookup від клієнта. Missing reference — generic label. Імена не копіювати в event/audit details. Existing audit `detailLabels` резолвить тільки `teamLead`, не всі ID (`server/services/audit.ts:35–37,115–131`); потрібен точний mapping, не generic «resolve all UUIDs».
- `components/settings/audit-field-label.ts:8–12` зараз повертає unknown identifier, а detail renderer має raw JSON fallback (`audit-record-sheet.tsx:112,143–147,324–333`). D137 має explicit labels/renderer і safe unknown fallback; title/location рендеряться React text, без HTML/Markdown, click links чи unsanitized tooltip. Title не вводити в списковий entityLabel, notification, error, log або change_feed. Existing invalidation вже opaque IDs (`server/events/index.ts:230–243`).
- Ні request bodies, raw validation input, driver messages, hashes rich text чи diff snapshots у pino/Sentry/CI attachments. UI приватні значення не стають статичними labels для CI privacy reporter. CI-LOG-01 файли лишаються без змін.

## Purge / removal: можливість проти реалізації

**Факт baseline:** `entity_event_pii.event_id` — PK/FK (`server/db/schema.ts:364–373`); SQL grants + trigger дозволяють `app_purge` видалити side row та виставити before/after **разом NULL**, зберігаючи інші audit колонки незмінними (`0000_narrow_inhumans.sql:293–300,329–336`). `app_rw` не може цього зробити. Немає процедури, vacancy purge permission/route, ledger або виконаного purge test. Напис «purgeable» означає підтримку сховища, не вже виконувану функцію. Soft delete не є purge.

**Eligibility — окремо від storage.** Рекомендований чинний policy gate: тільки Admin aal2, ресурс уже в **Deleted archive**, typed confirmation, ARCH-04 checklist (`docs/PRD.md:320–324`); history cleanup є частиною purge цього ресурсу, не новою кнопкою на live vacancy. D137 схвалює purgeability значень, але **не** авторизує standalone history purge активної вакансії. Якщо потрібен такий flow, власник має обрати: (A) Deleted-only, рекомендовано як чинна політика; (B) окремий live-history erasure flow з явно схваленими eligibility/retention/confirmation правилами. До рішення B заборонений. Немає питання про звуження salary до names-only; D80+D137 лишаються чинними.

**Запропонований D137 selector:** server-validated `V` і спільний strict vacancy boundary вище, включно draft-era/cancel reason/legacy vacancy events **лише** в цьому allowlist. Audit selector: `entity_type='vacancy' AND entity_id=V::text AND candidate_id IS NULL AND action IN` тому самому точному списку з восьми `vacancy.*` actions; не prefix match. Audit не має sensitivity колонки: action-specific projection обов'язковий, не blanket assumption GENERAL. Обнулювати обидва blobs лише вибраних audit rows. Закріпити цю версію allowlist у manifest; майбутні bonus/purge/restore actions потребують окремого review, не автоматичного включення.

Коректні candidate/application/interview/offer subjects, які лише корелюють із `V`, **не читаються і не видаляються** цим selector, навіть із GENERAL; для них потрібен окремий схвалений resource purge/checklist. Якщо запис стверджує vacancy subject, але має mismatched subject_id/vacancy_id, candidate/application correlation, невідомий type або unexpected sensitivity, reader відкидає його без summary, а purge preparation зупиняється з безпечним diagnostic IDs та review/remediation gate. Не розширювати selector для «очищення всього пов'язаного», не заявляти повний resource purge за неперевірених ambiguous rows. Це також не candidate purge і не каскадне видалення вакансії; `candidate.purge` не дає цього доступу.

Майбутня процедура: SECURITY DEFINER, `app_purge` owner, fixed search_path, narrow EXECUTE, без app_purge credentials у web app. Міграція має дати least-privilege **і SELECT GRANT, і RLS SELECT policy** на потрібні envelope колонки `entity_event`, та контрольований доступ до eligibility/manifest. Metadata inspection для preparation має бачити також rejected/ambiguous envelopes, correlated із server-validated `V`, щоб виявити порушення; вона не читає їх payload/side data і не додає їх у erase manifest. Політика повинна дозволяти цей diagnostic join, а erase function все одно застосовує strict subject/type boundary. Одного GRANT недостатньо: RLS увімкнено для всіх app tables (`0000_narrow_inhumans.sql:313–315`), поточні purge policies є лише для side/audit (`:331–336`). Не надавати BYPASSRLS, не вимикати RLS/triggers, не видаляти immutable events/audit rows.

**Стабільна serialized erasure boundary (майбутній механізм).** Prepare під users→vacancy lock і fresh policy check фіксує operation UUID, DB lineage, `V`, policy/schema version та **точні множини event IDs і audit IDs**, вибрані boundary в одному узгодженому snapshot; це manifest без values, з digest/counts. Boundary — ці множини, не `occurred_at`, wall-clock purge time чи повторний `WHERE vacancy_id=V`: identity allocation сама по собі не є commit order. Усі relevant vacancy writers дотримуються того самого lock protocol; prepared manifest незмінний. Pending purge fence не дозволяє restore ресурсу/зміну eligibility між prepare та apply; durable intent після підтвердженої авторизації вже не можна «скасувати» відновленням старого DB стану. Після prepare нові законні записи поза fenced resource/за окремим approved flow мають інші IDs і не входять до цієї операції. Для Deleted resource eligibility додатково забороняє нові edits. Повноту resource purge при finalization перевіряють окремо; виявлені нові relevant rows не включають мовчки в стару операцію.

Після durable journal acknowledgement, описаного нижче, apply знову бере locks, перевіряє manifest/digest/lineage та policy і транзакційно видаляє side rows **тільки** за зафіксованими event IDs та NULL-ить before/after **тільки** за audit IDs, повторно перевіряючи boundary. DB completion ledger та safe purge audit пишуться в цій транзакції. Повтор з тим самим operation UUID читає той самий manifest, ніколи не перевизначає cutoff; missing side row/вже NULL — idempotent success. Нове erasure потребує нового operation UUID та нової авторизації. Rows, створені пізніше за легальним flow, повтор старої операції зберігає.

Після видалення side row event/fields/actor/time лишаються, values недоступні; audit before/after NULL включно version metadata. Не відновлювати old/new з поточного vacancy, попереднього audit, catalog або client cache. Якщо потрібна позначка «видалено», брати її з підтвердженого purge ledger; missing side row сам по собі не доказ purge. Перевірка очищає **обидві** копії V; labels не повинні воскресити erased position reference.

Existing assignment events з user IDs, creation public number, urgency/status enums і actor IDs залишаються immutable metadata. Це pseudonymous linkage, не обіцянка erase всіх user identifiers; users зараз не purged за ADR-003 `:60`. User anonymisation/actor identity removal — окрема політика, не вирішується видаленням D137 side row. Видалення history values не означає очищення поточного title/location в основній vacancy: повний resource purge потребує окремого checklist її live колонок. Candidate purge не повинен стирати shared vacancy salary/history лише тому, що кандидат колись мав application.

**Restore prerequisite / R2.** Local `purge_log` із restored backup не є authoritative: backup, зроблений до erasure, не містить пізнішого запису. Запропонований механізм — окремий durable append-only erasure journal **поза DB snapshot і його restore domain**, з operation UUID, lineage, immutable exact-ID manifest/digest і ordered checkpoint; без raw values/free text, з restricted admin access. IDs лишаються confidential pseudonymous metadata, не «неперсональними» даними. Підтверджений durable write **erasure intent перед DB apply** — необхідний gate: його збій блокує apply. Intent означає бажане стирання, тому pending/failed-after-intent операції також replay-яться; завершення в DB не є єдиним джерелом правди. Prepare job до durable intent не вважається виконаним purge. Потрібні retry/reconciliation journal↔DB і контроль втрати/відкату журналу; конкретний зовнішній storage та його операційні гарантії ще не обрано/не реалізовано, і цей review їх не обіцяє.

Restore тримає застосунок закритим: зберегти authoritative journal поза rollback, зупинити erasure producers на cutover, перевірити його повноту до підтвердженого актуального checkpoint, звірити lineage/IDs, replay усіх relevant acknowledged intents на restored rows і лише потім відкрити доступ. Відсутні rows — no-op; інший lineage, remapped IDs без перевіреного mapping, відсутній/неповний журнал або невідомий tail — **fail closed**, не запуск із backup-local ledger. При separately retained/replayed законній пізнішій історії її original IDs зберігаються, identities advance без reuse; exact manifests її не стирають. Якщо цей durable mechanism не готовий, дозволеного безпечного restore prerequisite нема: не заявляти restore-safe purge і не відкривати відновлені дані після відомого erasure. Caches/export copies та backup retention теж потребують runbook. Без selector/procedure/journal integration proof допустимо лише «stored in purgeable columns; purge/restore flow pending», не повне закриття D137.
