# Security review — change email of a not-yet-activated user

Date: 2026-11-02. Scope: STORY-ROLE-05-7, ROLE-05, D44/D69/D70/D72; `PUT /api/v1/users/{userId}/email`, «Змінити email» dialog, seed change for the pending invitee. Static review of the uncommitted slice; test execution is coordinated by the orchestrator/QA.

## Verified controls

| Control                                           | Evidence / result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin + aal2 only, 404 otherwise                  | `targetUserId` (`invite-manage.ts:38-43`) → `requirePermission('settings.users.manage')` (`server/authz/permissions.ts:130`, GLOBAL + MFA) runs before any read. Tests: HEAD_RECRUITER/FINANCE → 404, aal1 Admin → `MFA_REQUIRED`, unknown/malformed id → 404, nothing written (`tests/integration/settings-user-email.test.ts:293-330`).                                                                                                                                                                                                                                                                                                                                                      |
| State guards under lock                           | `activatedAt` → `USER_ACTIVATED` is checked before `isActive` → `USER_DEACTIVATED` (`invite-manage.ts:218-219`), so an activated-then-deactivated user gets `USER_ACTIVATED` as the story requires. Unchanged address → 400 `EMAIL_UNCHANGED`. Missing/invalid roles → 409 `INVITE_ROLES_INVALID` before any write, and the old link keeps working.                                                                                                                                                                                                                                                                                                                                            |
| Race vs old-link acceptance (magic link + Google) | Change locks the PENDING invite, then the user. Acceptance locks invite + user in one `FOR UPDATE` by hash, then re-checks status, expiry, email and roles. If the change wins, the old row is REVOKED and its email ≠ expected ⇒ `INVITE_INVALID`. If acceptance wins, EvalPlanQual skips the now-ACCEPTED row, the user lock reads `activated_at` ⇒ 409 `USER_ACTIVATED`. The 4-round concurrency test asserts exactly one winner and no deadlock (`settings-user-email.test.ts:743`). Google callback: `completeInviteGoogle` re-reads the invite and requires the verified Google email to equal the **current** invite email (`invite.ts:388`). On failure the Supabase session is ended. |
| Race vs resend / revoke / re-invite / create      | Resend first: the change then revokes the rotated row, and the resent link is dead. Change first: resend's `UPDATE … status='PENDING'` finds nothing ⇒ `INVITE_NOT_PENDING`. Revoke first: the change creates a new invite (allowed for «Відкликано», D69). Re-invite serialises on the user lock. A concurrent invite of the same new address hits `app_user_email_uq` ⇒ mapped to the 409 field error (`invite-manage.ts:266-270`). `user_invite_pending_uq` keeps ≤ 1 PENDING invite.                                                                                                                                                                                                       |
| Token handling                                    | A fresh 256-bit token is generated and only its SHA-256 hash is inserted (`invite-manage.ts:212, 235-242`). The old row becomes REVOKED in the same transaction. The token goes only into the email fragment to the **new** address after commit, and never into the response, event, audit or logs. Nothing goes to the old address.                                                                                                                                                                                                                                                                                                                                                          |
| Old-link holder learns nothing                    | `inviteState` returns INVALID for non-PENDING rows (`server/auth/invite-token.ts:30`), so `inspectInvite` with the old token never shows the new address. Revoke and email update commit atomically, so no snapshot pairs the old hash with the new email.                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Email normalisation                               | One shared `emailAddressSchema` (trim + lower-case + Zod email ≤ 254, ASCII) for invite, login and change. DB `app_user_email_chk` enforces `email = lower(trim(email))`. Acceptance and Google use `emailsMatch` (trim + lower-case, plus-addresses distinct). The comparisons are consistent.                                                                                                                                                                                                                                                                                                                                                                                                |
| PII                                               | Event payload is strict `{inviteId, revokedInviteId, roles}` (`server/events/index.ts:41-47`). Old/new email goes only to `entity_event_pii` (`invite-manage.ts:250`) and audit `before/after` (Admin aal2 `audit.read`). The user «Історія» view never reads the PII row and shows the action only (D72, unit test). Route logs carry operation/actor/status/timing only. The mail-failure log has error name/code only, and a test asserts no address or link appears. The users-list `q` URL carrying an email is pre-existing and accepted in AS-06a (strip in Sentry when it lands).                                                                                                      |
| Purge readiness                                   | The audit before/after email and the PII side row are covered by the T-D11/DG-20 checklist. Any future staff-user anonymisation must include `user.email_changed` audit rows.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| CSRF / input                                      | Shared route factory: trusted Origin + `X-CSRF-Protection`, strict body (extra `roles`/`token` → 400), bounded uuid param.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Seed                                              | `server/db/seed/auth.ts` no longer creates an auth user for `pendingInvite` entries, so the demo pending invitee stays truly unlinked. Seeding stays behind `assertDisposableLocalData`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

Verdict: **APPROVED** for the bounded email-change slice, subject to the orchestrator's automated checks. SEC-EML-01 (orphan auth-user reconcile) goes into `docs/PROGRESS.md` as a tracked gap. SEC-EML-03 must be handled when deactivation lands.
